# T3 · 复杂代码与架构 · 遗留系统现场报障修复

`repo/` 是一套正在生产环境跑的制造质检系统（MES）后端。功能都齐、公开测试全绿，
但现场陆续报来一批"说不清但确实不对"的问题。请你作为接手的后端工程师，定位并修复它们。

## 环境与运行

- Python ≥ 3.10，仅标准库（用到内置 `sqlite3`）。
- 无需安装依赖；`python -m pytest -q` 可跑公开测试。

## 冻结契约（先读 `repo/CONTRACT.md`）

以下文件**不得修改**，判分会核对哈希，改动即判定提交物不合规、**不进入计分**：

- `repo/CONTRACT.md`
- `repo/tests/test_public.py`
- `repo/SPEC.md`

`repo/src/faults.py` 里登记的故障注入点是契约的一部分，**不许删除**（可以新增，请同时登记）。

**如果你发现测试本身写错了、或者锁死了错误的期望值 —— 不要改它。** 把这件事写进对应问题的答复 `notes` 里。

## 现场报障

### 现象一 · 明明有货，系统说不够料

仓库反映：领料时系统总说"库存不够"，可货架上明明有货。比如台账记了 2 千克的货、
需求单填 1.2 千克，系统有时候判不够、有时候又能发得出去。

### 现象二 · 模板改了版，老单子内容反而跟着变

工艺模板升了新版，维护界面看也是新版。可**新建**的批次套出来还是旧内容；
更奇怪的是有些**早就建好**的老批次，内容反而跟着新版变了。

### 现象三 · 主单的资料跑到子单名下

主单上传的图纸、工艺卡，会出现在它下属批次（子单）的资料列表里，还被标成是**子单自己的**。
财务按资料归属出归档清单时对不上数。

### 现象四 · 两张单共用一道工序，报工记录乱套

热处理是几张单共用的工序。忙时几个人同时用手持机报工，事后发现：有的记录**跑到别的单上**去了，
有的**多出来一模一样的一条**，还有**执行记录列表和这张单的汇总数字对不上**。

### 现象五 · 盘点做完，三个地方的数字对不上

盘点走完复核、审定、对账后，同一个物料能看出三个数：**台账余额、复核录入的实盘数（换算过来）、
对账汇总页**三边打架。此外海外仓按"克"复核、本部台账按"千克"记；
几个人同时复核同一张盘点单时，还出现过**有人录的数不见了、数对上了名字却记成别人**。

### 现象六 · 会签走乱：有的卡住、作废了还能往下走

单据要走四段会签（初审 → 中间两段并行 → 终审），中间能驳回重走、也能整单作废。
最近出现：并行两段几个人同时点，结果有的单**终审莫名批过了**，
也有**两段都批了却卡在终审**；被**驳回重走**的单只重批了初审就被当成"全批完"；
**整单作废**的单**还能继续走**；**看板显示的段位跟实际对不上**。

## 提示

- 报障人是运营、仓库、财务、车间班组长，可能缺乏专业素养。
- **"一个人顺序操作从不出错、多人/跨单位/流转时才出错"是很强的线索。**
- 仓库里其它随手写的说明文档不一定是最新的。
- 判断标准：一张表如果丢了能从核心表原样重算出来，它就是派生表（可随意重建）；否则是核心表（不许改语义）。

## 交付

1. 修好的整个 `repo/` 目录（冻结文件保持原样）。
2. `repo/_answers/` 目录，**每修一个问题放一个 JSON**：

```json
{
  "题目": "现象一",
  "verdict": "fixed",
  "rootCause": "一句话说清真正的根因",
  "evidence": ["读了哪个文件的哪一段，看到了什么"],
  "notes": "可选。发现测试或文档本身有问题写在这里。"
}
```

`verdict` 取值：`fixed`（是问题，已修复）/ `not-a-bug`（查证后认为不是问题）。

**如果你在通读代码的过程中发现了清单之外的其它问题，欢迎一并修复，并按同样格式补一个答复。**
把系统真正读懂，往往比只对着现象逐条排查更快。
